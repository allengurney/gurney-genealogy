# Plan 04 — Simple graph-enhanced evidence drawer

Status: expanded design direction, revised 2026-07-05 against the implemented
SQLite graph, static website export, prose-marker contract, and graph editor;
revised 2026-07-06 (Claude review with Allen) — implementation began alongside
Plan 03's annex build for the Cloudflare preview.

## 0. Decisions accepted 2026-07-06

1. **Visibility decision made:** Allen approved flipping all current research
   items and prose markers to `visibility='public'` in the live DB (bulk
   decision, recorded through the audited editor path, one revision).
   Source-excerpt publication is NOT bulk-flipped: `excerpt_publishable`
   stays per-source-link and defaults closed, so excerpts continue to require
   an affirmative per-excerpt decision. Future items still default
   `repo_only`; publication remains an explicit step per item.
2. The D0 assumption "use synthetic data until visibility decisions are
   approved" is superseded — the real export is populated.
3. Export JSON is copied into the site's passthrough assets at
   `/assets/g13-graph/` (markers index, per-marker bundles, per-finding
   JSON). The drawer fetches one bundle per open; nothing graph-wide loads
   with a topic page.
4. Permanent evidence and finding pages are generated by the Plan 03 package
   sync from the export JSON, through the ordinary Eleventy layouts — the
   exporter's minimal fallback HTML is never copied into `_site`.
5. Direction-aware relationship labels and grouping live in one shared
   module (`assets/g13-graph-labels.js`) consumed by both the build-time page
   generator (Node) and the browser drawer.

This plan extends:

- Plan 01's canonical SQLite research graph and public-export safety contract.
- Plan 2a's invisible prose markers and compact **Evidence** link.
- Plan 03's static topic-structured research annex.
- The implemented G5 static website export.

It does not turn the public website into the graph editor. The editor is a
useful presentation reference, but the public drawer is deliberately much
simpler.

## 1. Decisions accepted 2026-07-05

1. A prose marker renders as the compact word **Evidence**, not an item count or
   a row of graph terminology.
2. Selecting **Evidence** opens a restrained right-side drawer on desktop and a
   near-full-height bottom sheet on mobile.
3. The initial view explains the marked passage with plain-language findings,
   sources, material qualification, and a small set of related items. It is not
   a graph dashboard or editing form.
4. Links between related research items are interactive. Selecting one replaces
   the contents of the same drawer; it never opens drawers inside drawers.
5. Drawer traversal maintains a small history trail, updates browser history,
   and works with Back/Forward. Every link remains an ordinary permanent link
   when JavaScript is absent.
6. Raw graph IDs are implementation details. Do not show them in headings,
   chips, link text, or the ordinary drawer. They may appear inside an optional
   **Technical details** disclosure and may remain in stable URLs and JSON.
7. Borrow the graph editor's semantic item-kind palette, adapted to the public
   site's light/dark surfaces and accessibility requirements. Color never
   carries meaning alone.
8. The graph enhancement remains optional. Removing JavaScript and graph JSON
   leaves a complete research annex with ordinary citations and permanent
   evidence pages.

## 2. Implemented foundation

The framework is sufficiently solid to plan against:

- SQLite is canonical for research items, item relations, marker membership,
  source links, dates, negative-result scope, entities, and publication state.
- Markdown owns exact prose-marker placement.
- Marker bundles require one public primary item and complete public membership.
- `export-website` already emits deterministic public findings, marker bundles,
  adjacency data, and permanent fallback HTML.
- Export fails closed when a public marker cannot be emitted completely.
- Relationship edges export only when both endpoints are public.
- Evidence excerpts export only after an affirmative publishability decision.
- Numeric confidence and repo-internal review/location fields do not enter the
  public export.
- The graph editor already demonstrates item-kind colors, directional
  relationship navigation, source-role wording, and deep-linked item selection.

Plan 04 therefore adds a reader-facing projection and interaction layer; it
does not redesign graph storage or create a runtime graph service.

## 3. Reader contract

Footnotes and Evidence links coexist:

- A footnote answers: **Where did this statement come from?**
- Evidence answers: **Why does the project believe this, and what supports,
  qualifies, or challenges it?**

Do not emit an Evidence link when the graph adds no useful reasoning,
qualification, conflict, negative result, or exploratory path beyond the
adjacent citation.

The first Evidence link on a page should have accessible help text explaining
the distinction. The annex landing page should explain it once in visible
language.

## 4. Evidence-link behavior

Generated HTML remains an ordinary link:

```html
<a class="evidence-link"
   href="/research/evidence/g13-pm-000003/"
   data-evidence-id="G13-PM-000003"
   aria-label="Evidence explaining the Tyng farm conclusion">
  Evidence
</a>
```

The marker ID may remain in `href` and `data-*` as stable plumbing, but is not
reader-facing text.

Without JavaScript, the link opens the site-native permanent evidence page.
With JavaScript:

1. Prevent ordinary navigation.
2. Load the marker bundle from the static export.
3. Open the drawer/sheet and move focus to its heading.
4. Add an evidence state to browser history.
5. On close, return focus to the triggering Evidence link.

If loading fails, follow the ordinary `href`. Do not leave the reader in an
empty or partially populated drawer.

## 5. Simple initial drawer

The initial marker-bundle view should normally contain:

```text
Evidence                                      [Close]

[Finding] Arrival at Weymouth

John probably arrived between 1638 and early 1641.

Confidence: Moderate-high

Why this conclusion
  • At Weymouth by 2 June 1641
  • Not present in the reviewed 1636 property list
  • Original grantee of three early parcels

Material qualification
  Anderson assigns arrival in 1636

Sources
  Massachusetts Bay Records, vol. 1, p. 331
  Weymouth Land Grants Book, pp. 12, 23, 31

Related
  [Depends on] Weymouth residence
  [Qualified by] Anderson's 1636 assessment

Full research treatment · Open full screen

Technical details ▸
```

Display rules:

- Lead with the primary item's short label and statement.
- Show its reader-facing kind label.
- Show status or confidence only when it adds meaning.
- Prefer the graph item's concise summary when one exists.
- Show at most three to five entries in each relationship/source group before
  **View all**.
- If a marker expresses several items, show the primary first and place the
  others under **Also covered here**. Do not present a tabbed mini-database.
- Omit empty sections.
- Never display raw `item_kind`, relation codes, source roles, or graph IDs in
  the ordinary view.

## 6. Item-kind visual language

Borrow the editor's semantic palette:

|---|---|---|
| Evidence | `source_evidence` | Cyan `#56b6c2` |
| Finding | `research_finding` | Green `#3ecf8e` |
| Analysis | `analysis` | Violet `#a78bfa` |
| Identity hypothesis | `identity_hypothesis` | Pink `#e08fd0` |
| Negative result | `negative_result` | Slate `#8fa3b8` |
| Evidence conflict | `evidence_conflict` | Orange `#f0883e` |

| Project conclusion | `project_statement` | Gray `#9aa5b1` |

These are semantic reference hues, not an instruction to copy the editor's dark

Every colored chip also carries its text label. Conflict, negative-result, and
open-question states must remain distinguishable in grayscale and to screen
readers.

## 7. Relationship projection

The database relation is directional. The website translates the same edge
differently depending on which endpoint the reader is viewing:

| Stored relation | From-item label | To-item label |
|---|---|---|
| `SUPPORTS` | Supports | Supported by |
| `CONTRADICTS` | Conflicts with | Conflicts with |
| `QUALIFIES` | Qualifies | Qualified by |
| `DEPENDS_ON` | Depends on | Required by |
| `ELIMINATES` | Rules out | Ruled out by |
| `SUPERSEDES` | Replaces | Replaced by |
| `CONTEXTUALIZES` | Provides context for | Context from |
| `SAME_EVENT_AS` | Same event as | Same event as |
| `POTENTIALLY_SAME_PERSON_AS` | Possibly same person as | Possibly same person as |
| `DISTINCT_FROM` | Distinct from | Distinct from |
| `PUBLISHED_AS` | Published as | Publication of |
| `SUMMARIZED_IN` | Summarized in | Summarizes |
| `REQUIRES_REVIEW_OF` | Requires review of | Review required by |
| `ANALYZES` | Analyzes | Analyzed by |
| `SYNTHESIZES` | Synthesizes | Synthesized by |
| `WEIGHS` | Weighs | Weighed by |
| `INFORMS` | Informs | Informed by |

These labels are presentation vocabulary, not new stored relation types.

Group relationships for readers:

1. **Why this conclusion** — support, dependency, synthesis, analysis.
2. **Qualifications and conflicts** — qualification, contradiction,
   elimination, review requirements.
3. **Development of the conclusion** — supersession and publication mapping.
4. **Related context** — contextual, event/person equivalence, distinction, and
   other informative links.

Relationship strength and bearing may influence ordering, but should not become
a dense row of technical badges. Show an edge explanation as a short secondary
line only when it clarifies why the relationship matters.

## 8. Clicking a related research item

Every related-item title is a normal link to its permanent finding page. With
JavaScript enabled:

1. Push the current drawer target onto the drawer history.
2. Fetch or retrieve the selected public finding.
3. Replace the current drawer contents in place.
4. Keep the drawer open and move focus to the new heading.
5. Update browser history so Back restores the previous drawer item.

Do not:

- open a nested drawer;
- replace the underlying topic page;
- draw a node-link visualization;
- expose incoming/outgoing edge jargon;
- show a dead link for a restricted or non-public endpoint.

The drawer header should show a compact trail such as:

```text
Evidence › Arrival at Weymouth › Anderson's 1636 assessment
```

Keep only the current path, not a permanent breadcrumb taxonomy. Provide a
drawer-level Back control after the first pivot. Browser Back and the control
must produce the same result.

Closing the drawer returns to the underlying topic page and restores focus.
Opening the permanent page is always available and supports opening in a new
tab.

## 9. Other links

Keep the first implementation deliberately bounded:

- Research-item relationships traverse inside the drawer.
- **Full research treatment** navigates to the relevant annex topic and heading.
- Sources link to an existing or future canonical source page when one exists;
  otherwise show the full citation without inventing a page.
- People link to canonical ancestor/subject pages.
- Places link to canonical place pages.
- Publication appearances link to the published page and heading.

Source, person, and place links use ordinary page navigation rather than
turning the drawer into a universal object browser. That can be revisited only
if reader testing demonstrates a real need.

## 10. Machine IDs and technical details

Stable IDs remain necessary for graph identity, URLs, JSON lookup, debugging,
and durable links. They are not meaningful public labels.

Default view:

- no item or marker IDs in headings;
- no ID-only relationship links;
- no monospaced ID chips;
- no graph revision, schema version, or raw relation code;
- no repository path.

An optional collapsed **Technical details** disclosure may show:

- item or marker ID;
- graph revision used for the page;
- permanent machine-readable JSON URL;
- raw relation type when useful for audit;
- last reviewed or updated date if the public contract supplies one.

Do not put IDs into accessible names merely because they exist in the DOM.
Short label is the preferred link text; the statement is the fallback.

ID-based permanent URLs are acceptable for KISS and stability. A second public
slug identity layer is not required merely to hide IDs from ordinary page
content.

## 11. Static data and site integration

The implemented G5 export remains the data source:

```text
canonical SQLite graph
        |
        v
validated public static export
        |
        +--> findings index and per-item JSON
        +--> marker index and per-marker bundles
        +--> public-only relationship edges
        |
        v
Plan 03 package adapter / Eleventy
        |
        +--> site-native permanent evidence pages
        +--> site-native permanent finding pages
        +--> page marker-to-bundle lookup
        +--> small drawer JavaScript and CSS
```

Use the Plan 03 adapter and existing site layouts to create fallback pages.
The minimal HTML currently emitted by `export-website` is a plumbing proof, not
the final public template. Do not maintain a separate visual system for graph
pages.

The browser should fetch only the selected marker/finding payload. Do not load
the full adjacency export on every topic page. A compact page manifest may map
marker IDs to static bundle URLs.

The website layer may add reader labels, grouping, resolved source citations,
canonical person/place URLs, and display ordering. It must not modify or infer
new graph facts.

### 11.1 Permanent-page contract

The permanent evidence page is the fully expanded, no-JavaScript equivalent of
the marker drawer. It includes:

- primary finding/analysis and any other items expressed by the marker;
- reader-facing kind, status, confidence, and meaningful date ranges;
- grouped support, qualification, conflict, dependency, and supersession;
- complete public sources with citations, locators, and cleared excerpts;
- full research-treatment link;
- ordinary links to every public related finding;
- working-research disclaimer;
- collapsed Technical details.

The permanent finding page shows the same treatment for one research item,
including its complete public relationship neighborhood and every public
publication appearance. It must not imply that an isolated graph item replaces
the fuller topic narrative.

Both page types use normal site chrome, canonical extensionless URLs,
breadcrumbs, index/search metadata, and ordinary hyperlinks. Public pages enter
the sitemap and `llms.txt`; preview pages remain `noindex` and excluded.

## 12. Export adjustments to review before implementation

Audit the existing G5 payload before building the UI:

- Add or compute direction-aware reader relationship labels in one shared
  presentation mapping.
- Ensure each related public item has a short label or safe statement fallback.
- Resolve `sourceId` values to full public citation text at build time without
  duplicating source truth.
- Supply topic public URLs/headings rather than repository paths.
- Confirm dates expose only historically meaningful public fields; synthetic
  chronology keys must not be displayed as evidence.
- Confirm graph IDs and revision metadata are available for technical details
  but absent from ordinary presentation.
- Keep the existing fail-closed visibility and excerpt rules unchanged.

Prefer presentation enrichment in the site adapter where it depends on site
routes or canonical data. Add fields to the graph export only when they are
stable graph-derived public data needed by more than one consumer.

## 13. URL and history model

KISS baseline:

- Evidence link `href`: permanent marker page.
- Related-item `href`: permanent finding page.
- JavaScript state: one open drawer target plus its in-drawer path.
- `history.pushState`: opening a marker and each related-item pivot.
- `popstate`: restore the prior item, marker, or closed state.
- Reload/deep link: permanent page remains the authoritative shareable target.

The topic URL need not become a complicated encoded graph path. If a lightweight
query/hash state is used for restoring an open drawer, it carries one current
marker/item ID, not the entire traversal history.

## 14. Accessibility and responsive behavior

Desktop:

- right-side drawer;
- readable width, approximately 28–36rem;
- underlying page remains visually present but not keyboard-active while the
  modal drawer is open.

Mobile:

- near-full-height bottom sheet or full-height panel;
- single-column sections;
- persistent close/back controls;
- no hover-dependent behavior;
- no horizontal scrolling except inside inherently wide source tables.

Required behavior:

- semantic dialog labeling;
- focus moves into the drawer on open;
- focus is trapped while modal;
- `Escape` closes;
- close restores the triggering link;
- keyboard and touch targets meet site standards;
- screen readers announce content changes after a relationship pivot;
- relationship links make sense out of context;
- color is never the sole status signal;
- reduced-motion preference removes slide animation;
- failed JavaScript falls through to ordinary links.

## 16. Validation

Build and runtime tests must prove:

- Every emitted Evidence link resolves to a complete public marker bundle.
- Every related-item link resolves to a public finding page and JSON payload.
- No non-public item label, ID, count, or edge leaks.
- Excerpts appear only when publishable.
- Direction-aware labels are correct for both endpoints of every relation type.
- Missing short labels fall back to readable statements, never bare IDs.
- Ordinary drawer markup contains no raw graph IDs except inside Technical
  details and unavoidable link/data plumbing.
- Opening, pivoting, Back/Forward, closing, and focus restoration are
  deterministic.
- Failed fetch follows or exposes the permanent page.
- No-JavaScript pages contain the complete public evidence treatment.
- Topic pages remain readable and fully cited with the enhancement removed.

## 17. Acceptance criteria

The enhancement succeeds when:

- A general reader understands what Evidence adds beyond a footnote.
- The first drawer view is short, plain-language, and useful.
- A reader can follow **Depends on**, **Qualified by**, and other relationships
  without encountering graph vocabulary or losing their place.
- Related-item selection reuses one drawer and Back behaves as expected.
- Machine IDs are not prominent.
- The editor's useful semantic colors survive without importing editor
  complexity.
- Permanent pages and ordinary links make the experience robust without
  JavaScript.
- The public annex remains the primary reading experience; the graph remains a
  selective explanatory layer.
- No runtime database or API is required.

## 18. Explicitly deferred

- Public node-link graph visualization.
- Graph editing or review controls.
- Revision-history comparison UI.
- Full-database search inside the drawer.
- Turning sources, people, and places into nested drawer object browsers.
- Automatic graph-generated prose.
- Broad rollout to other ancestors before the G13 pilot is accepted.
